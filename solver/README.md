# Решатель лабиринтов на C++

Это твоя часть проекта. Go-обёртка уже готова: она умеет читать лабиринт,
проверять его, запускать твою программу и рисовать найденный путь.
Чего в ней нет — самого поиска пути. Его пишешь ты.

## Как всё устроено

Go-часть запускает твою программу как отдельный процесс и общается с ней
через стандартные потоки:

```
лабиринт ──▶ stdin ──▶ [ твоя программа ] ──▶ stdout ──▶ путь
```

Со твоей стороны это обычные `std::cin` и `std::cout`. Никаких библиотек,
сетей и чужого кода читать не нужно.

Точный формат описан в [`../docs/PROTOCOL.md`](../docs/PROTOCOL.md).
Прочитай его до того, как начнёшь писать код — это **контракт**:
договорённость, которую мы оба обязаны соблюдать, иначе части не состыкуются.

Правила работы с ветками и PR — в [`../docs/WORKFLOW.md`](../docs/WORKFLOW.md).

## Чеклист

Отмечай пункты по мере прохождения — в том же PR, что и сама работа.
Каждый пункт, кроме нулевого, это **отдельная ветка и отдельный pull request**.
Не делай всё сразу одним большим PR: смысл упражнения в том, чтобы научиться
показывать работу небольшими понятными порциями.

У каждой задачи есть «Проверка» — команда и ожидаемый результат. Это значит,
что спрашивать «я правильно сделал?» не нужно: ты можешь ответить себе сам.
Спрашивать стоит другое — «я не понимаю, почему так» и «я застрял вот здесь».

### [ ] 0. Окружение

Ничего коммитить не нужно. Задача — убедиться, что всё работает, **до** того
как ты напишешь первую строчку. Если что-то сломается потом, ты будешь знать,
что дело в твоём коде, а не в машине.

```
git clone <ссылка на репозиторий>
cd edu-team-pet-project
go test ./...
go run ./cmd/maze -input testdata/corner.txt
g++ --version
```

**Проверка.** `go test` печатает `ok` для двух пакетов, `go run` рисует
лабиринт с путём из звёздочек, `g++` сообщает свою версию.

Если спотыкается на первых двух — нужен Go (https://go.dev/dl/). Если на
третьей — компилятор C++: на macOS `xcode-select --install`, на Ubuntu
`sudo apt install build-essential`.

### [ ] 1. Эхо

Создай `solver/main.cpp`, который читает лабиринт со stdin и печатает его
обратно в stdout без изменений. Алгоритмов тут нет совсем: задача целиком
про git — ветка, коммит, push, pull request, обсуждение, merge.

```
g++ -std=c++17 -O2 -o solver/solver solver/main.cpp
./solver/solver < testdata/simple.txt
```

**Проверка.** Вывод совпадает с содержимым `testdata/simple.txt`
байт в байт. Сравнить можно так — команда молчит, если файлы одинаковые:

```
./solver/solver < testdata/simple.txt | diff - testdata/simple.txt
```

---

### [ ] 2. Сборка одной командой

Добавь `solver/Makefile`, чтобы сборка запускалась как `make -C solver`.
Хватит одного правила и цели `clean`. CMake не нужен — к нему вернёмся
позже отдельной задачей, когда станет понятно, зачем он.

**Проверка.** `make -C solver clean && make -C solver` собирает бинарь
с нуля, эхо из задачи 1 по-прежнему работает.

---

### [ ] 3. Поиск пути

Теперь сам алгоритм. Нужен **кратчайший** путь по числу клеток, ходы
на 4 стороны. Подходящий инструмент — поиск в ширину (BFS): очередь клеток,
отметки о посещённых и запоминание, откуда мы пришли в каждую клетку,
чтобы в конце развернуть путь назад от цели к старту.

Вывод — строго по протоколу: `OK <N>`, затем `N` строк с координатами.

**Проверка.** Запусти на одном лабиринте эталонный решатель на Go и свой:

```
go run ./cmd/maze -input testdata/corner.txt
go run ./cmd/maze -input testdata/corner.txt -solver ./solver/solver
```

Длина пути должна совпадать — это главный критерий. Сам путь может
отличаться: кратчайших путей бывает несколько, и это нормально.
Прогони так все файлы из `testdata/`.

Если Go-часть ругается «решатель вернул некорректный путь» — она уже
проверила твой ответ за тебя и в сообщении написано, что именно не так:
разрыв в пути, проход через стену или не та начальная клетка.

### [ ] 4. Отказы и ошибки

Два разных случая, которые легко перепутать:

- **пути нет** — лабиринт правильный, но до цели не добраться.
  Печатай `NO_PATH` и выходи с кодом `0`. Это не ошибка.
- **лабиринт испорчен** — размеры не совпадают с сеткой, нет старта,
  две цели, посторонний символ. Пиши сообщение в `std::cerr` и выходи
  с кодом, **отличным от нуля**. В stdout при этом ничего не печатай.

**Проверка.**

```
./solver/solver < testdata/no_path.txt            # NO_PATH
echo $?                                            # 0

printf '3 1\n#S#\n' | ./solver/solver              # сообщение об ошибке
echo $?                                            # не 0
```

Во втором случае в лабиринте нет цели. Подумай, почему сообщение должно уйти
в stderr, а не в stdout — ответ есть в `../docs/PROTOCOL.md`.

приходи с файлом, разберём вместе.

## Если застрял

Это ожидаемая часть работы, а не признак провала. Полезный порядок действий:

1. Перечитай `../docs/PROTOCOL.md` — больше половины расхождений оттуда.
2. Посмотри, что именно получает твоя программа:
   `cat testdata/corner.txt` — ровно это приходит в stdin.
3. Сравни с эталоном на том же файле: разница в выводе покажет, где ты
   отклонился от контракта.
4. Напиши мне — но вместе с вопросом пришли команду, которую запускал,
   и то, что она напечатала. Так разговор займёт пять минут вместо часа.
