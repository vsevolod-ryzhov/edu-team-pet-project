# Как мы работаем

Короткий документ про договорённости. Они не выводятся из кода — их можно
только прочитать, поэтому прочитай один раз и возвращайся по необходимости.

## Правила

1. **В `main` не коммитим.** Любая работа — в отдельной ветке.
2. **Один pull request — одна задача** из чеклиста. Маленький PR проверяют
   за десять минут, большой лежит неделю.
3. **`git push --force` не используем.** Если что-то пошло не так — напиши,
   разберёмся вместе. Потерянную историю не восстановить.
4. **Ревью — это разговор, а не оценка.** На комментарий можно ответить
   «не согласен, потому что...». Это нормальный и ожидаемый ответ.

## Один цикл работы

```
git switch main
git pull                       # забрать то, что уже влилось
git switch -c solver-echo      # ветка под задачу

# ... пишешь код ...

git status                     # что изменилось
git diff                       # что именно изменилось
git add solver/main.cpp        # добавляем по файлам, не "git add ."
git commit -m "solver: читает лабиринт и печатает его обратно"
git push -u origin solver-echo
```

Дальше GitHub в ответ на push покажет ссылку «Create a pull request» —
открывай её. В описании напиши, что сделал и как это проверить.
После merge:

```
git switch main
git pull
git branch -d solver-echo      # ветка больше не нужна
```

## Имена

Ветки: `solver-echo`, `solver-makefile`, `solver-bfs` — что делаем, без фамилий
и номеров задач.

Коммиты: первая строка — до ~70 символов, в настоящем времени, по-русски или
по-английски, но единообразно. Сообщение отвечает на вопрос «что изменится,
если это применить»: `solver: добавлен поиск пути в ширину`, а не `fix`,
`исправления` или `работа за вторник`.

## Если возник конфликт

Конфликт — это не поломка. Git просто не знает, какой из двух вариантов
правильный, и спрашивает тебя.

```
git switch main
git pull
git switch solver-bfs
git merge main
```

Если git сообщил о конфликте, он отметил спорные места в файлах:

```
<<<<<<< HEAD
твой вариант
=======
вариант из main
>>>>>>> main
```

Нужно открыть файл, оставить правильный текст (иногда — оба варианта вместе),
убрать строки с `<<<<<<<`, `=======`, `>>>>>>>`, затем:

```
git add <файл>
git commit
```

Чего делать не надо: удалять репозиторий и клонировать заново. Так конфликт
не решается, а прячется — и в следующий раз случится там же.

## Чего не делать молча

- Менять `docs/PROTOCOL.md` — это общая договорённость, меняем вдвоём.
- Менять файлы в `cmd/` и `internal/` — это Go-часть.
- Удалять или переписывать чужие тесты, чтобы «прошли».

Во всех трёх случаях не нужно спрашивать разрешения — нужно сказать, что
мешает. Умение договариваться о границах тут и есть предмет упражнения.
